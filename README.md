# NurLife — CRM для оптово-розничной торговли

Next.js 15 (App Router, TypeScript strict) + Supabase (Postgres, Auth, Storage, RLS, Realtime, pg_cron).
Интерфейс полностью на русском, тёмная чёрно-золотая тема (есть светлая), адаптив от 360 px.

## Что умеет

| Модуль | Возможности |
|---|---|
| Каталог | Дерево категорий (3 уровня), карточка товара, оптовые ступени «от N → цена», до 10 фото (сжатие до 1600 px в браузере), поиск/фильтры, импорт XLSX с проверкой ошибок, экспорт XLSX, массовое изменение цен |
| Клиенты | Опт/розница, реквизиты, контакты, индивидуальные цены и скидка, кредитный лимит, отсрочка, долг и просрочка, заказы, платежи, акт сверки (печать/PDF/XLSX), история изменений, проверка дублей по телефону/ИНН |
| Заказы | Автоцена (индивидуальная → ступень → опт/розница → скидка клиента), статусы Новый → Подтверждён (резерв) → Собран → Отгружен (списание по себестоимости) → Оплачен (автоматически), отмена и возврат, частичные оплаты и авансы (FIFO), таблица и канбан |
| Быстрая продажа | `/sale`: подбор/сканер, оплата, чек — одной транзакцией (`quick_sale`) |
| Печать | Товарный чек (A4 и 80 мм), счёт на оплату, расходная накладная, акт сверки; печать и PDF, сумма прописью |
| Склад | Остатки и резервы, приход по скользящей средней, корректировки с причиной, инвентаризация с мобильным вводом, «Нужно заказать», журнал движений |
| Закупки | Поставщики, закупки (черновик → заказана → принята, частичная приёмка), создание из «Нужно заказать», долг поставщику, история закупочных цен |
| Платежи и касса | Входящие (по заказу или аванс), исходящие поставщикам, прочие приходы/расходы, сторно, балансы касс |
| Дашборд и отчёты | Выручка, заказы, средний чек, маржа, прибыль, дебиторка, низкие остатки; продажи по периодам, маржа по товарам/категориям, топ-20, возраст дебиторки, продажи по продавцам, стоимость склада, ABC; экспорт XLSX |
| Уведомления | Колокольчик в реальном времени: новый заказ, смена статуса, низкий остаток и просрочка (ежедневно в 09:00 по Екатеринбургу) |
| Аудит | Журнал изменений с диффом «было → стало» |
| Сотрудники | Приглашение продавцов по e-mail (лимит 5), деактивация с передачей клиентов |

### Роли

| | Владелец | Продавец |
|---|---|---|
| Розничные/оптовые цены, остатки, все заказы и клиенты | ✓ | ✓ |
| Закупочные цены, себестоимость, маржа, прибыль, стоимость склада | ✓ | — |
| Товары, цены, склад, закупки, поставщики, кассы, аудит, настройки, сотрудники | ✓ | — |
| Скидка/кредитный лимит/отсрочка/индивидуальные цены клиента | ✓ | только просмотр |
| Скидка в заказе | без ограничений | до `settings.seller_max_discount` (по умолчанию 10 %) |
| Откат статуса, отмена отгруженного (возврат), сторно платежа | ✓ | — |

Ограничения действуют в трёх местах: интерфейс, middleware и база данных (RLS, триггеры, проверки внутри rpc). Продавец физически не может прочитать закупочные цены: таблицы `products`, `stock`, `order_items`, `stock_movements` для него закрыты, он читает представления `*_public`, `catalog_items`, `order_lines`.

## Быстрый старт (локально)

Нужны Node.js ≥ 20.12 и Docker.

```bash
npm install
npx supabase start                     # локальный Supabase, применит все миграции
npx supabase status                    # покажет API URL, anon key и service_role key
cp .env.example .env.local             # впишите ключи из status
npm run db:types                       # (необязательно) перегенерировать типы БД
npm run dev                            # http://localhost:3000
```

### Первый вход — владелец

Регистрация закрыта, поэтому владельца создаём один раз вручную:

1. Studio (http://localhost:54323) → Authentication → Users → **Add user** (e-mail + пароль, «Auto confirm»).
2. SQL Editor:
   ```sql
   update public.profiles
      set role = 'owner', full_name = 'Ваше ФИО'
    where id = (select id from auth.users where email = 'you@example.com');
   ```
3. Войдите в приложение → **Настройки**: реквизиты компании и банка (для чека, счёта, накладной).
4. **Сотрудники** → «Пригласить продавца». Локально письма видны в Inbucket: http://localhost:54324.

## Развёртывание

### 1. Supabase (облако)

```bash
npx supabase login
npx supabase link --project-ref <ref>
npx supabase db push                   # применит все миграции
```

В панели Supabase:

- **Authentication → Sign In / Providers**: отключите «Allow new users to sign up».
- **Authentication → URL Configuration**: Site URL = адрес на Vercel; в Redirect URLs добавьте `https://<домен>/auth/confirm`.
- **Authentication → Emails → Templates**: тексты писем «Invite user» и «Reset password» возьмите из `supabase/templates/*.html` — ссылки ведут на `/auth/confirm`.
- **Database → Extensions**: убедитесь, что включён `pg_cron` (миграция включает его сама, если доступно). Проверка: `select * from cron.job;` — должны быть задачи `nurlife-low-stock` и `nurlife-overdue-debts`. Если их нет, выполните блок про pg_cron из миграции `20261025140500_notifications_audit_users.sql` в SQL Editor.
- Владельца создайте так же, как локально (Authentication → Users → Add user, затем SQL выше).

### 2. Vercel

1. Импортируйте репозиторий в Vercel (фреймворк определится как Next.js).
2. Environment Variables:
   - `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` — Project Settings → API;
   - `SUPABASE_SERVICE_ROLE_KEY` — **только серверная** переменная, без `NEXT_PUBLIC_`;
   - `NEXT_PUBLIC_SITE_URL` — адрес приложения (для ссылок в приглашениях);
   - `NEXT_PUBLIC_SENTRY_DSN`, `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_AUTH_TOKEN` — по желанию (без DSN мониторинг выключен).
3. Deploy. Регион функций лучше выбрать ближе к региону базы Supabase.

### 3. Резервные копии

- Supabase делает ежедневные бэкапы (на платных тарифах — с PITR).
- Дополнительно `.github/workflows/backup.yml` раз в неделю снимает `pg_dump`, шифрует его (AES-256) и хранит как артефакт 90 дней. Добавьте секреты репозитория `SUPABASE_DB_URL` (строка подключения, режим Session) и `BACKUP_PASSPHRASE`.
- Восстановление: `gpg -d nurlife-ГГГГ-ММ-ДД.dump.gpg > db.dump && pg_restore --no-owner -d "<url>" db.dump`.

## Тесты

| Команда | Что проверяет |
|---|---|
| `npm test` | Vitest: расчёт цены и лимит скидки, форматирование денег/дат, сумма прописью, контраст палитры WCAG AA (обе темы) |
| `npm run db:test` | pgTAP (211 проверок): схема и триггеры, RLS и доступ продавца, полный цикл заказа/склада/оплат, FIFO, сторно, быстрая продажа, закупки, инвентаризация, отчёты, уведомления, аудит |
| `npm run test:e2e` | Playwright: вход и роли, быстрая продажа и чек, лимит скидки 10/11 %, цикл заказа до «Оплачен», телефон 360 px |

Для e2e нужен **тестовый** стенд: владелец и продавец (`E2E_*` в `.env.local`), `SUPABASE_SERVICE_ROLE_KEY` и `E2E_ALLOW_SEED=1` — перед запуском создаётся товар `E2E-001` с остатком. Не запускайте e2e на боевой базе.

CI (`.github/workflows/ci.yml`) на каждый push: проверка типов, Vitest, сборка, миграции и pgTAP на чистой базе.

## Как устроено

```
supabase/
  migrations/        22 миграции: схема → RLS → бизнес-логика → отчёты → уведомления/аудит
  tests/database/    pgTAP-тесты
  templates/         письма приглашения и восстановления пароля
src/
  app/(app)/         разделы приложения (за входом)
  app/print/         печатные формы (белый фон, без меню)
  app/api/users/     приглашение и блокировка сотрудников (service role, только сервер)
  components/        UI-компоненты (shadcn-стиль), таблицы, подбор товара/клиента, печать/PDF
  lib/               Supabase-клиенты, форматирование, расчёт цены, XLSX, типы БД
tests/unit, tests/e2e
```

**Бизнес-операции — только в Postgres.** Статусы заказов, резерв и списание, приход, корректировки, оплаты и их распределение выполняются rpc-функциями в одной транзакции с `select … for update`: `save_order`, `change_order_status`, `quick_sale`, `register_payment`, `allocate_payment`, `void_payment`, `post_receipt`, `post_adjustment`, `post_inventory` и др. Остатки меняются только через `_stock_apply`, каждое изменение пишется в неизменяемый `stock_movements`.

**Деньги** — `numeric(12,2)`, количества — `numeric(12,3)`, время — `timestamptz`. Для штучных единиц дробное количество запрещено в БД.

**Номера документов** — `З-ГГГГ-000001` (заказы), `П-…` (закупки), `К-…`/`И-…` (корректировка/инвентаризация); счётчик без пропусков, год — по Екатеринбургу (`app_timezone()`).

**Права на функции.** Миграции отзывают `EXECUTE` у `PUBLIC`/`anon` по умолчанию: новую rpc нужно явно открыть `grant execute on function … to authenticated`. Это защищает служебные функции от вызова через API.

**Изменение схемы** — только новой миграцией: `npx supabase migration new <имя>`, затем `npm run db:types`.

### Принятые решения

- Анонимная розничная продажа: `orders.client_id` может быть пустым (оптовый заказ — только с клиентом).
- `credit_limit = NULL` — без ограничения (в том числе у клиентов, заведённых продавцом); проверка лимита при подтверждении заказа, владелец может превысить.
- Оплаты распределяются по заказам таблицей `payment_allocations`; излишек — аванс, он автоматически зачитывается в следующие подтверждённые заказы (FIFO). Отмена заказа возвращает оплату в аванс.
- Скидка клиента из карточки (её задаёт владелец) не входит в лимит скидки продавца; лимит считается от автоцены с учётом и скидки, и ручного снижения цены.
- Индивидуальная цена клиента окончательная — скидка клиента к ней не применяется. Оптовые ступени действуют только в оптовых заказах.
- Возврат (отмена отгруженного заказа, только владелец) возвращает товар на склад по себестоимости продажи.
- При приёмке закупки закупочная цена товара обновляется на цену последней приёмки.
- Документы склада: позиции закупки редактируются только в черновике.
- Шрифты: Philosopher (заголовки) и Manrope (текст) через `next/font`; в PDF встроен Inter (кириллица, лицензия OFL — `public/fonts/OFL-Inter.txt`).
- Не реализовано по ТЗ: налоги, фискальные чеки, интеграции, бухучёт, портал клиента, несколько складов.
